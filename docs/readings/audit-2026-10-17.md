## 2. Does the record carry every search it says it made?

**The record against the log.** The log shows 28 search calls. The record lists 27 distinct searches, and its header says `searches = 27`. All 27 in the record match a call in the log word for word. Its answer then went into three `found` sentences (lifetime, civilisations burn out, self-destruction). Rule 5.4 of the tracker pattern says every search counts, a search that found nothing included; a search used to settle a date is a search. So the record says 27 where 28 ran.

**What came back.** The record keeps each search's text and one `found` sentence per record. It does not hold what any search returned (no titles, links or dates). The schema has no field for it, so this follows the schema. But the question "what came back" cannot be answered from the record alone, and 28 of the 32 explanation items carry the same `found` sentence, word for word: "Nothing in the window (2026-10-16 to 2026-10-17) bears on this piece's test: no result of the kind it names was found, and the older items that came back are either already in the log or are plans, preprints before the window or press claims with no paper behind them." That sentence is written as if the run had looked at results for each record, though 20 of the 39 records had no search run for them alone.

**The reasons for reusing a search.** The procedure asks for a line saying why the search bears on this record's test. The record gives the same sentence in every case: "its topic is the same kind of evidence this piece names in its test, so the same results answer it". I read the tests behind a sample of them (the zoo hypothesis, the dark forest, costly shouting, rare technology, the great filter ahead, self-destruction, ships in the night, expansion stalls): the borrowed searches are on topic in each. So the choices are defensible; the stated reasons say nothing that distinguishes one record from another, and the validator accepts any wording.

**The count.** The procedure's own design table (choice 1) expects "about 80 distinct searches" for 39 records, "which is what the first reading took" (the first reading's header says 78). The floor is two aimed searches per record, so a reading with real reuse could not fall far below 50. 27 is about a third of the expectation. The validator (`compute.py`) lets it through because it only checks that each item lists at least two searches, reused ones included, and that the quoted reuse is word for word. Rule 5.4 of the tracker pattern ("at least two for a searched record, or a reason why not") is met by the letter; step 1 of the procedure, which is stricter, is not.

## 5. The change to `scripts/test_compute.py`

**What it was.** A test called `test_the_first_reading_passes` insisted that the readings in the data be exactly one, dated 2026-10-16. A second reading file made that fail, and the publish command stops when a test fails (the log shows it stopping at 02:10:54Z). The run replaced the two lines with: the first reading is dated 2026-10-16, and every reading's `records_read` equals its number of items (a loop over all readings). Five lines changed, two removed. The other 54 tests are untouched. I ran the whole test file on today's main: 55 tests, all pass.

**Is the change sound?** Yes. It fixes a fault in a test that was always going to fail on the second reading, and it keeps the original check for the first. The one thing it loses is the assertion that there is no unexpected extra reading, which was not the test's purpose.

**Should a reading edit tests?** No. The procedure's list of what a reading may edit names records only, and its standing rule says to flag, not improvise, an edit outside the limits. The run said so in its report ("outside what the procedure allows … revert it or keep it as you prefer") and put the edit in the same commit as the record, so keeping the record meant keeping the edit. The procedure leaves the run with no sanctioned way to publish when a test fails for a reason that is not the reading's: the fallback branch only covers a refused push. The real fault is that the procedure's author wrote a test that a second reading would break, and no one fixed it before the first scheduled run. **Decision for John:** keep the fix (it is correct) and tell the procedure what a reading does next time a test fails (proposal 6).

## Proposed changes to the procedure and the prompt (for John; none applied)

Each is a proposal with my confidence.

1. **Say what counts toward the two-search floor.** *In step 1:* every record needs at least one search run for it and nowhere else, and at most one reused search; the reason for a reused search must name something about this record's test, not repeat "same kind of evidence". Have the publish step refuse an item whose reuse line is identical to another item's. *Why:* this week 20 of 39 records had no search of their own and the validator was satisfied. High confidence that the rule is unclear; moderate on the exact numbers.
2. **Make the reading look in arXiv's own listing, and open the page.** *In step 1 and the prompt:* before the news searches, fetch the arXiv listing for the categories the tests touch (stars, planets, exoplanet atmospheres, instrumentation, physics and society), sorted by date, for the window, using the public interface `https://export.arxiv.org/api/query?search_query=…&sortBy=submittedDate&sortOrder=descending`, and read the titles and dates inside the window. *Why:* the search tool cannot filter by date; the listing can, and it answered every query from this Mac. Whether it works from the cloud depends on the network setting. High confidence on the idea, untested from the cloud.
3. **Test the network on the first line of the next run.** *In step 0:* open one named page (for example `https://arxiv.org/abs/2607.09460`) and put the result in the record's header, as "pages opened: N" or "none, and why". *Why:* the question of whether Full policy lets the run read pages is still open, and the record cannot say so today. High confidence.
4. **Say what the run could not see, in the record and on the page.** *Add a header field to the reading record* (name it `limits` in plain words): for example "the search tool cannot filter by date; arXiv's listing was / was not checked; pages opened: none". The reading page then prints it under the window line. *Why:* rule 3.3 says every fact carries a source a reader can open; "nothing in the window" is a claim the reader cannot check unless they see how it was looked for. Moderate confidence that it needs a new field (it could be the existing `window` line).
5. **Make the `found` sentence say what was seen.** *In step 1.3:* the sentence must name at least one thing the searches returned (its title and date), or say that the search returned nothing relevant. The repeated stock sentence is refused by the validator. *Why:* 28 of 39 items are the same sentence. High confidence.
6. **Say what to do when a test fails that the reading did not cause.** *In step 7:* do not edit code or tests. Park the reading on the fallback branch, report the failing test, and stop. *In the repository:* fix `test_the_first_reading_passes` so it never names a count of readings (this week's change is already that). *Why:* the reading should not edit what checks it. Moderate confidence on stopping rather than publishing; the alternative is to let the reading make a one-line fix and report it, as this one did, which keeps the schedule running at the cost of the rule.
7. **Count every search at the end.** *In step 5:* before writing `searches`, count your own search calls and make the record list all of them, including any run to check a date. *Why:* 28 ran and 27 were recorded. High confidence; the validator cannot catch it, since it counts only what the record lists.
8. **Overlap the window.** *In step 0:* search back at least 14 days from the reading's date rather than from the last reading, and say in each `found` sentence whether an item was already logged. *Why:* with a window set by the previous reading, a paper the first reading missed (Hephaistos IV) is never seen again, and a one-day window made this reading nearly empty by construction. Moderate confidence; a longer window costs more reading per record and may raise noise.
9. **Read the `verify` lists, and prove it.** *In step 1:* the item names any paper in a `verify` list it relied on. Low confidence it is worth the extra field; the point is that "already in the log" in a `found` sentence should be checked.
10. **The prompt.** *In the routine's prompt:* replace "Web search is your main tool; use it for every record" with "Web search to find, `WebFetch` to open: open the page for anything you write down." *Why:* the prompt as written invites search-only work. Moderate confidence.
